# LLM Wiki — 知识库宪法

你是这个知识库的 AI 维护者。
你的职责是将 `raw/` 层的原始内容**编译**成 `pages/` 中结构化、互联的知识页面，并持续维护这个不断增长的知识网络。

> **核心理念**：知识被编译一次，然后持续更新——而不是每次查询时重新推导。
> Wiki 是一个持续积累的产物。交叉引用已经建好，矛盾已经被标记，综合分析已经反映了所有已读内容。

---

## 架构：三层分离

```
raw/              原始来源（只读层）
                  来自 harvest 技能或用户手动添加的文档。
                  LLM 只读取，不修改正文。仅在 .meta.json 中标记编译状态。

pages/            编译后的 Wiki 页面（LLM 所有层）
                  LLM 创建、更新、维护交叉引用。用户阅读和浏览。

WIKI.md           本文件（Schema 层）
                  定义规范、约定、工作流。你和 LLM 共同演进。
```

---

## 目录结构

```
wiki/
├── WIKI.md                本文件
├── index.md               内容目录：按分类列出所有页面及摘要
├── log.md                 操作日志：按时间记录事件
├── raw/                   原始文档（只读）
│   ├── _index.json        元数据索引
│   └── {YYYYMMDD}/{keyword}/
│       ├── {src}_{hash}.md         全文 + frontmatter
│       └── {src}_{hash}.meta.json  元数据侧车
├── pages/                 编译后的 Wiki 页面
│   ├── overview/          概览页（可包含多个维度，如：整体介绍视角、技术架构视角、用户手册视角等）
│   ├── concepts/          概念页（技术范式、方法论、抽象思想）
│   ├── entities/          实体页（人物、工具、公司、产品）
│   └── syntheses/         综合分析页（跨来源趋势判断、深度对比分析）
└── signals/               低质量碎片
```

## 操作模式

### 1. Compile（深度编译与原子化提取）

扫描 `raw/` 下所有 `.meta.json` 文件，找到 `"compiled": false` 的文档。

在正式写入 `pages/` 之前，必须先生成并维护 `compile_plan.md`：

1. 运行 `compile_plan.py` 生成 Raw Coverage Checklist 和 Extraction Table。
2. 先读完整个 checklist，理解这批 raw 的全局信息景观。
3. 编译过程中持续填写 Extraction Table。不要只在脑中完成抽取。
4. 每个 raw 只有在其有效信息已进入至少一个目标页面，且页面中出现本地 raw 引用后，才能勾选并标记为 `compiled: true`。

**对每个尚未编译的文档，你必须执行以下深度提取流程：**

1. **阅读全文**：理解文档的核心论点、提到的每一个具体工具(Entity)和技术名词(Concept)。
2. **主动拆解**：**严禁仅做全文总结**。你必须基于文档内容，识别出其中涉及的所有独立实体和概念。
3. **原子化写入**：
   - 对于文档中提到的每个重要 **实体**：在 `pages/entities/` 中创建或更新对应页面。
   - 对于文档中提到的每个重要 **概念**：在 `pages/concepts/` 中创建或更新对应页面。
   - 对于文档的整体价值：如果文档是综述性或具有极高引导价值，更新 `pages/overview/` 中的相关页面。
4. **强链接与高密度引用**：
   - 在新创建的内容中，使用 `[[Page Title]]` 将相关的实体与概念互相链接。
   - **充分利用 Data Pool**：不仅引用核心文档，还应主动搜索 `raw/` 中其他提及该知识点的文档。
   - **必须**在"关键来源"章节引用文档对应的本地 raw 路径，格式为 `[[raw/YYYYMMDD/filename.md]]`。
5. **Overview 覆盖门槛**：所有 `urgent` / `high` 文档，以及 relevance >= 80 的文档，必须被至少一个 `pages/overview/` 页面吸收。Overview 不是目录简介，而是高权重资料的综合入口。
6. **编译后审计**：运行 `compile_audit.py`。如果出现 compiled raw 未被任何页面引用，或高权重 raw 未进入 overview，必须先修复，不要向用户声称编译完成。
7. **更新进度**：只有通过上述覆盖要求后，才更新 `.meta.json` / `raw/_index.json` 中的 `compiled: true` 并记录日志。

### 2. Query（检索回答）

当用户在知识库中提问、要求解释、对比、决策建议、查找依据、复盘某个主题时，进入本模式。

目标不是像搜索引擎一样返回片段，而是基于这个人的长期知识资产，重建一个可理解、可追溯、可行动的回答。

按下面顺序执行：

1. **理解问题意图**
   - 先判断用户要的是事实查询、概念解释、操作方法、方案对比、决策建议、历史脉络，还是复盘总结。
   - 识别问题中的核心对象、别名、上下位概念、时间范围和隐含目标。
   - 如果问题过宽，先给出你将采用的检索角度；只有在目标无法判断时才追问。

2. **规划检索路线**
   - 先读 `index.md`，确认知识库的导航结构和可能入口。
   - 优先读 `pages/overview/`，建立全局语境和主题边界。
   - 根据问题类型进入 `concepts`、`entities`、`syntheses`，并沿 `[[Wiki Links]]` 继续追踪相关页面。
   - 只有当页面依据不足、需要核对原始说法、或发现结论可能过时时，才回到 `raw/`。

3. **匹配知识对象**
   - 事实查询优先看 `entities` 和相关 raw 引用。
   - 概念解释优先看 `concepts`，并补充相关实体或实践场景。
   - 方案对比、趋势判断、选型建议优先看 `syntheses` 和多视角 `overview`。
   - 如果问题横跨多个对象，要按主题关系组织，而不是机械罗列文件内容。

4. **校验依据与时效**
   - 对关键结论检查是否能追溯到 `raw` 或明确的内部页面。
   - 区分“已被知识库沉淀的判断”“来自单个来源的事实”“当前资料不足的推测”。
   - 遇到冲突信息时，不要强行合并；说明冲突在哪里、哪个来源更新、哪个判断更可靠。
   - 如果问题依赖最新动态，而知识库没有近期 raw 或页面明显滞后，要明确提示需要运行 harvest 或维护更新。

5. **组织回答**
   - 先直接回答用户问题，不要先铺陈检索过程。
   - 再给出必要背景、判断依据、适用边界和可执行建议。
   - 回答中引用的关键知识点必须以 `[[Page Title]]` 呈现。
   - 对重要结论尽量给出来源链：`[[Page Title]]` -> `[[raw/YYYYMMDD/source.md]]`。
   - 如果答案不完整，要说明缺口是什么，而不是用泛化常识补齐。

6. **个人知识库原则**
   - 优先使用本知识库已经沉淀的定义、偏好、判断和实践经验。
   - 保留用户自己的术语、分类和历史决策，不要随意替换成通用百科口径。
   - 如果外部常识与知识库记录冲突，先说明差异，再建议是否需要更新知识库。

7. **对话知识回流判断**
   - 回答后执行一次轻量判断：这次问答是否可复用、是否形成新的判断路径、方法论、FAQ、实践经验。
   - 只有当内容相对稳定、有行动价值、被用户认可或有明确依据、且对现有 wiki 有真实增量时，才建议沉淀。
   - 不要自动把普通聊天记录写入知识库；如果用户确认沉淀，再进入 **Maintenance / Self-update** 模式。

### 3. Maintenance / Self-update（知识维护与自更新）

当用户要求维护知识库、更新知识、吸收新增资料、整理近期内容、做增量编译、沉淀高价值问答时，进入本模式。

目标不是重写整个知识库，而是围绕“增量信息”做定向更新，让知识库持续演进。

按下面顺序执行：

1. **发现增量**
   - 识别新增来源，包括 `raw/` 中新进入但未编译的资料、最近新增的内部文档、已确认的高价值问答。
   - 不做全库重写，优先处理新增或变化部分。

2. **判断影响范围**
   - 判断新增信息影响哪些知识对象：`overview`、`concepts`、`entities`、`syntheses`。
   - 如有需要，也可扩展到 `faqs`、`playbooks`、`practices`。
   - 先回答：这是补充事实，还是会改变已有判断？

3. **分级更新**
   - 事实类更新：优先更新 `entities`、索引、基础说明。
   - 认知类更新：更新 `concepts`、`overview`，吸收新机制、新变化、新关系。
   - 判断类更新：更新 `syntheses`，对比新旧信息，必要时修正原有结论。
   - 对高风险判断，不要无依据改写；必须说明触发更新的新增依据。

4. **对话知识回流**
   - 如果用户提问过程中的问题、回答、方法具有高价值，也可纳入候选知识。
   - 只有满足可复用、相对稳定、有行动价值、对现有知识库有增量、有依据或已被用户认可时才建议沉淀。
   - 不要把普通聊天记录直接入库，要先提炼为知识对象或方法条目。

5. **更新后治理**
   - 更新 `index.md`，保证入口同步刷新。
   - 检查新增内容是否补齐来源引用。
   - 检查是否产生重复页、冲突页、碎片页。
   - 必要时给出“建议合并 / 建议升级为正式页面 / 建议保留为信号”的判断。

输出要求：

- 先说明本次发现了哪些增量。
- 再说明这些增量影响了哪些知识对象。
- 然后给出明确更新建议：应更新哪些页、应新增哪些页、哪些内容只适合保留为候选或信号。
- 如果用户要求你直接执行维护，再按上述原则完成更新。

注意：

- 自更新不是全量重写，而是面向受影响知识对象的定向重编译。
- 越靠近事实，越适合自动更新；越靠近判断，越需要谨慎。
- 沉淀的不只是答案，还包括高质量问题、判断路径和可复用方法。

### 4. Health Check（知识库健康检查）

当用户要求检查知识库健康度、做 health check、做巡检、检查质量、检查时效性、检查可用性时，进入本模式。

目标不是统计文件数量，而是判断这个知识库是否仍然“可导航、可理解、可信、可维护”。

按下面顺序执行检查：

1. **结构健康**
   - 检查 `wiki/index.md` 是否存在且能承担导航作用。
   - 检查是否存在 `overview` 页面，并能代表当前主题全貌。
   - 检查 `pages/` 下的知识对象分类是否清晰，是否混淆 `concepts`、`entities`、`syntheses`。
   - 检查是否存在孤儿页面、空页面、重复页面、重复概念或重复实体。

2. **内容健康**
   - 检查 `raw/` 中是否有长期未编译内容。
   - 检查页面是否过于空洞，是否只有标题或很少有效信息。
   - 检查综合页是否只是摘抄，还是已经形成归纳、比较或判断。

3. **时效健康**
   - 检查最近新增 `raw` 是否已经被关键页面吸收。
   - 重点检查 `overview`、`syntheses`、高频 `entities` 页面是否落后于新增资料。
   - 对技术追踪型知识库，优先关注“新事实是否进入 raw，关键认知页是否同步更新”。

4. **可追溯健康**
   - 检查关键页面是否能追溯到 `raw`。
   - 检查是否存在只有结论、没有来源依据的页面。
   - 检查引用链条是否完整。

5. **消费健康**
   - 模拟真实消费路径：`index -> overview -> concepts/entities -> syntheses -> raw`。
   - 判断常见问题是否能快速找到入口。
   - 如果必须频繁回到 `raw` 才能回答，说明知识编译不足。

输出要求：

- 先给总体结论：健康 / 基本健康 / 存在明显风险。
- 再按严重程度列出问题，优先列高风险问题。
- 每个问题必须说明：问题是什么、为什么影响知识消费或维护、建议怎么修。
- 最后给出一个简短的维护优先级列表：立即处理、本轮可处理、后续观察。

注意：

- 不要只做文件存在性检查。
- 不要把“有内容”误判为“健康”。
- 健康检查的核心，是检查知识是否还能被稳定导航、正确理解、可信判断和持续维护。

## 页面格式规范

### Overview 页（`pages/overview/{Topic}_{Perspective}.md`）
*根据 Data Pool 的深度，可以从不同维度创建概览。例如：全景概览、技术深度概览、社区评价概览等。*

```markdown
---
type: overview
title: "{Topic} {Perspective} 概览"
tags: [overview, main]
created: YYYYMMDD
updated: YYYYMMDD
---

# {Topic} {Perspective} 概览

## 简介
[对该知识库主题的宏观定义]

## 知识图谱入口
- **核心实体**: [[Entity A]], [[Entity B]]
- **关键概念**: [[Concept A]], [[Concept B]]

## 核心内容与多维总结
[基于 raw 数据总结的当前状态、核心功能、技术亮点、或社区反馈。请保持高度的知识密度，尽可能整合所有已入库的相关 raw 资料。]

## 关键来源
- [[raw/YYYYMMDD/src_hash.md]] — {描述该文档对概览的贡献}
- [[raw/YYYYMMDD/other_src.md]] — {补充信息说明}
```

### Concept 页（`pages/concepts/{Topic}.md`）

```markdown
---
type: concept
title: "Topic Name"
aliases: ["别名1"]
tags: [tag1]
sources: N
created: YYYYMMDD
updated: YYYYMMDD
---

# Topic Name

## 定义与核心思想
[描述其原理，必须引用 [[Related Entity]] 或 [[Related Concept]]]

## 关键来源
- [[raw/YYYYMMDD/src_hash.md]] — 核心定义来源
```

### Entity 页（`pages/entities/{Name}.md`）

```markdown
---
type: entity
entity_type: person | tool | company | product
title: "Entity Name"
tags: [tag1]
sources: N
created: YYYYMMDD
updated: YYYYMMDD
---

# Entity Name

## 概述
[简短介绍]

## 核心特性
- 应用了 [[Concept A]]
- 属于 [[Entity B]] 的产品线

## 关键来源
- [[raw/YYYYMMDD/src_hash.md]] — 详细技术规格见此处
```

## 写作规则（铁律）

1. **禁止外部链接**：在“关键来源”章节，**严禁引用 http/https URL**。必须引用本地路径 `[[raw/YYYYMMDD/source_file.md]]`。
2. **充分收割 (Crystallization)**：如果 raw 文档提到了一个新的工具或观点，即使不是当前文档的主角，也应在对应页面追加信息，确保 raw 文档的价值被榨干。
3. **高密度多维概览**：Overview 页面不应只是简介，应作为该库的“最强综述”。当知识面很广时，应拆分为不同视角的多个 Overview（如 `openclaw_architecture` vs `openclaw_user_feedback`）。
4. **覆盖先于完成**：`compiled: true` 是质量承诺，不是流程标记。未进入目标页面、未被本地 raw 引用、未纳入 overview 的高权重资料，都不能算完成。
5. **日期格式**：所有 frontmatter 和路径中的日期统一使用 `YYYYMMDD` 格式。
6. **双向链接**：创建页面时必须考虑“它属于谁”和“谁属于它”，通过双链构建网络。
